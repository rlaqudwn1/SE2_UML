# 시퀀스 배치 인터페이스의 부족한 부분 검토

검토일: 2026-10-14. 대상: `feat/diagram-model-kim-byeongju`의 [인터페이스](../src/main/java/org/se2uml/layout/SequenceLayoutEngine.java), [계약 검증](../src/test/java/org/se2uml/layout/SequenceLayoutContractCheck.java), [상세 계약](SEQUENCE_LAYOUT_CONTRACT.md), [설계 근거](INTERFACE_DESIGN_RATIONALE.md).

이 문서는 **김병주의 시퀀스 배치 입출력 계약에 대한 검토와 제안**이다. Java 25 LTS 데스크톱을 전제로 하며, 문법·파서·메시지·활성 구간의 의미 데이터 구조를 새로 정하지 않는다. 기존 Java 코드와 계약 문서를 변경하지 않았다. 아래 수치 예시는 계약의 빈틈을 설명하는 계산 사례이며 엔진 실행 결과가 아니다.

## 판단 요약

현재 인터페이스는 의미 모델과 배치를 분리하고 ID·순서·수동 위치 제약을 전달하는 출발점으로 적절하다. 그러나 **행의 전체 폭·높이만 전달하고 연결점 위치를 엔진이 자유롭게 정하는 계약은, 어댑터가 측정한 도형을 보존하기에 부족하다.** 실제 엔진보다 먼저 측정값과 연결점 사이의 관계를 합의해야 한다.

| 우선순위 | 부족한 부분 | 지금 필요한 결정 |
| --- | --- | --- |
| P0: 기본 기능의 계약을 확정하기 전 | 행의 전체 폭과 연결점 사이 필요 폭이 구분되지 않음 | 긴 기본 메시지를 어디에 수용하는지, 폭이 어떤 제약인지 정의 |
| P0: 자기 호출을 지원한다고 설명하기 전 | 중복 참여자 참조는 있지만 각 연결점의 행 내부 높이·돌출 방향은 없음 | 자기 호출의 측정 geometry를 전달하거나 최초 지원 범위를 제한 |
| P0: 구현 보장을 설명하기 전 | DTO 검사와 성공 배치 검증의 경계 | 현재 테스트의 보장 범위를 정확히 표시하고 엔진 검증 기준 합의 |
| P1: 노트 지원을 넣을 때 | 왼쪽·오른쪽 노트의 돌출량이 구분되지 않음 | 연결점 기준의 좌우 점유 영역 전달 |
| P1: 편집기 연결 전 | 순서·간격·pin 충돌의 구체 기준, 진단 대상의 이름 공간 | 충돌 예시와 처리 규칙 합의 |
| 후속 범위 | 같은 높이의 복수 요소, 중첩 프레임, 활성 구간, 생성·소멸 등 | 필요 기능이 확정된 시점에 최소한으로 확장 |

P0는 모든 기능을 지금 구현하라는 뜻이 아니다. **기본 메시지·자기 호출을 지원하는 계약으로 합의하거나 발표하기 전에 결정해야 할 사항**이다. 노트나 동높이 배치를 첫 버전에서 제외한다면 이를 명시하는 것만으로 당장의 범위를 줄일 수 있다.

## 현재 구현과 아직 제안인 보장

| 항목 | 코드 또는 테스트에서 확인한 것 | 아직 확인되지 않은 것 |
| --- | --- | --- |
| 입력 | 크기·유한수·ID·참조 검증, 리스트 순서 보존, 컬렉션 복사 | 측정값만으로 실제 도형을 배치할 수 있는지 |
| 자기 호출 | 같은 참여자 ID를 여러 번 넣을 수 있음 | 두 연결점의 서로 다른 높이, 루프 돌출 영역 |
| 수동 위치 | 고정/선호 구분과 요청 좌표를 값으로 보존 | 엔진 결과가 실제 pin을 보존하는지 |
| 결과 | Map과 중첩 List의 불변 스냅샷, 수치 검증, `hasErrors()` | 누락 ID, 순서, 간격, 연결점 위치, 캔버스 포함 검사 |
| 진단 | WARNING/ERROR 데이터와 오류 유무 판별 | 실제 충돌 발견과 적절한 진단 생성 |
| 알고리즘 | `layout(request)` 메서드 계약 | 구현체·렌더링·저장·드래그 동작 |

검토 중 `/tmp/se2-uml-jdk25/bin`을 PATH에 추가하고 `bash scripts/check-model.sh`를 실행해 **Java 25 컴파일과 기존 계약 검증 통과**를 확인했다. 스크립트는 `--release 25 -Xlint:all -Werror`로 컴파일한다. 최초 실행에서는 기본 PATH에 `javac`가 없었으며, 기존 임시 JDK를 지정해 재실행했다. 이 통과를 실제 배치 알고리즘의 정확성으로 해석하면 안 된다.

## 1. 행의 폭만으로는 긴 기본 메시지의 배치를 설명할 수 없다

현재 성공 조건은 `rowBounds.width >= LayoutRow.width`이고 연결점이 행 안에 있으면 된다. **행의 폭을 늘리는 것과 두 참여자의 중심 간격을 늘리는 것은 다르다.**

다음 수치는 현 계약의 기하 조건을 만족하는 예다.

| 항목 | 값 |
| --- | --- |
| 참여자 A / B | 각각 `Bounds(0, 0, 80, 30)` / `Bounds(100, 0, 80, 30)` |
| 옵션 | 참여자 간격 20, 행 간격 10, 헤더 간격 15, 여백 10 |
| 입력 행 | 참조 `[A, B]`, 폭 240, 높이 40 |
| 결과 행 | `Bounds(-30, 100, 240, 40)` |
| 연결점 | `(40, 110)`, `(140, 110)` |
| 캔버스 | `Bounds(-40, -10, 260, 160)` |

행의 폭은 240이지만 연결점 사이는 100뿐이다. 렌더러가 폭 220의 라벨을 두 연결점 사이에 놓기로 했다면 수용할 수 없다. 반대로 라벨이 연결점 밖으로 나가도 되는 스타일이라면 가능한 배치일 수 있다. **현재 입력으로는 두 정책을 구분할 수 없다.**

최소 제안은 `width`가 전체 점유 폭인지, 연결점 사이 최소 거리인지 먼저 합의하는 것이다. 둘 다 필요하면 전체 영역과 별도로 연결점 쌍의 최소 가로 거리 정보를 전달한다. 최소 거리는 참여자 순서와 연결점 참조 순서가 반대인 응답에도 적용되도록 정의해야 한다. 메시지 종류를 엔진에 추가할 필요는 없다.

Mermaid의 조사 대상 커밋은 메시지 폭을 참여자의 가로 간격 계산에 반영한다. 이것은 전체 행 경계를 크게 만드는 일과 별개라는 비교 근거다. [Mermaid `calculateActorMargins` 원본](https://github.com/mermaid-js/mermaid/blob/4f6ac96ac95fd0ee0f66c986985680eb98dce1ec/packages/mermaid/src/diagrams/sequence/sequenceRenderer.ts#L1603-L1667). 다만 이 구현을 우리의 표준 알고리즘으로 채택해야 한다는 뜻은 아니다.

## 2. 중복 참조만으로 자기 호출의 측정 결과가 전달되지는 않는다

현재 `LayoutRow("self", [A, A], 80, 60)`은 두 연결점의 x를 같은 참여자 중심에 놓을 수 있다. 그러나 y는 모두 엔진 재량이다. 현 계약만 따르면 두 점을 같은 y에 놓아도 된다.

예를 들어 동일한 폭 80·높이 60의 두 도형이 다음 연결점을 요구할 수 있다.

| 측정 결과 | 첫 연결점의 행 내부 y | 둘째 연결점의 행 내부 y | 나머지 공간 |
| --- | --- | --- | --- |
| 도형 S1 | 10 | 40 | 아래쪽 장식·패딩 20 |
| 도형 S2 | 25 | 55 | 위쪽 라벨 공간 25 |

현재는 둘 다 같은 `LayoutRow`로 변환된다. ID에 숨은 의미를 넣거나 엔진·렌더러가 별도 암묵 규칙을 공유하지 않는 한, 엔진은 두 측정 결과를 구분할 수 없다. 엔진이 반환한 두 y를 렌더러가 임의로 고치면 결과 연결점이 실제로 그린 점과 달라진다.

최소 제안은 **참조 순서별 연결점의 행 내부 y 오프셋**을 전달하고 결과가 이를 보존하도록 정하는 것이다. 보통 메시지의 두 오프셋은 같고 자기 호출은 다를 수 있다. 이는 `SelfMessage` 같은 의미 타입을 정의하는 일이 아니다. 루프가 어느 쪽으로 얼마나 나가는지도 행의 점유 영역과 연결해 전달해야 한다.

모든 연결점의 로컬 x를 고정한 뒤 행 전체를 단순 평행이동시키는 설계도 주의해야 한다. A와 B를 사용자가 벌릴 때 일반 메시지는 가로로 늘어나야 하기 때문이다. **참여자 중심에 종속되는 x, 행 내부에서 보존하는 y, 필요한 돌출량을 구분**하는 정도로 시작하는 편이 작다. 활성 박스 테두리에 연결하는 x 오프셋은 해당 기능이 필요할 때 추가할 수 있다.

외부 도구가 자기 호출을 지원한다는 사실은 [PlantUML 공식 시퀀스 문서의 Message to Self 예시](https://plantuml.com/sequence-diagram)에서 확인했다. 우리의 중복 ID 허용이 그 도형 처리까지 구현했다는 근거는 되지 않는다.

## 3. 노트의 전체 크기는 좌우 돌출 위치를 알려주지 않는다

참여자 중심을 상대 x=0으로 두자. 폭 120의 노트가 연결 기준점에서 10만큼 떨어져 있다면 다음 두 영역은 다르다.

| 표시 | 실제 노트 영역 | 연결 기준점까지 포함한 배치 영역 |
| --- | --- | --- |
| 왼쪽 노트 | `[-130, -10]` | `[-130, 0]` |
| 오른쪽 노트 | `[10, 130]` | `[0, 130]` |

두 행 모두 참조 `[A]`, 폭 130, 같은 높이로 전달될 수 있다. 총폭만으로는 어느 쪽 경계를 늘려야 하는지 알 수 없다. 왼쪽 노트인데 오른쪽 공간만 예약하면 캔버스가 실제 그림을 포함하지 않을 수 있다.

여기서 노트의 기준점은 화면에 그리는 연결선 끝이 아닐 수 있다. **배치용 기준점과 눈에 보이는 선 끝을 동일하게 해석해야 하는지**도 합의해야 한다. 현재 계약이 모든 anchor를 rowBounds 안에 요구하므로 위 예시는 기준점까지 포함한 배치 영역으로 계산했다.

최소 제안은 한 기준점 또는 참조 범위에 대한 좌우 돌출량을 측정해 전달하는 것이다. 의미 담당자는 왼쪽/오른쪽 노트 여부를 관리하고, 어댑터는 그 결정과 측정값을 숫자로 바꾼다. 엔진이 노트 문법이나 의미 종류를 판단할 필요는 없다. 보수적으로 양쪽 모두 큰 여백을 예약하는 임시 방법도 있지만, 조밀한 배치와 실제 필요 여백을 보장하는 계약으로 설명해서는 안 된다.

Mermaid 공식 문서는 노트의 왼쪽·오른쪽·겹침 위치와 두 참여자에 걸치는 경우를 명시한다. 이는 우리에게 당장 모든 노트를 구현하라는 요구가 아니라, 크기만으로 부족한 사례의 근거다. [Mermaid Notes](https://mermaid.js.org/syntax/sequenceDiagram.html#notes).

## 4. `par`와 같은 높이 배치는 다른 요구다

[Mermaid Parallel](https://mermaid.js.org/syntax/sequenceDiagram.html#parallel)의 `par … and … end`는 병렬 동작을 블록으로 표현한다. 이 사실만으로 모든 분기 메시지가 같은 y여야 한다는 결론은 나오지 않는다. 의미적 병렬을 화면에서 세로로 나누어 표시할 수 있으며, 세로 표시 순서 전체를 의미상 선후 관계라고 단정해서도 안 된다.

한편 [PlantUML 공식 시퀀스 문서](https://plantuml.com/sequence-diagram)의 `Parallel messages (with teoz)` 절은 `!pragma teoz true`와 `&`로 병렬 메시지를 표시하는 별도 예시를 제공한다. [공식 예시 이미지](https://plantuml.com/imgw/img-57a728919221d22d7e02ad3e7ca182db.png)에서 두 메시지 선이 같은 높이에 놓인 것을 직접 확인했다. [Teoz 설명](https://plantuml.com/teoz)도 이 표기를 다룬다. **같은 높이의 복수 메시지를 요구하는 경우**에는 현재의 행별 전역 비겹침 규칙과 충돌한다.

현재 행 높이는 양수이고, 다음 행은 이전 행의 아래 경계에 `rowGap >= 0`을 더한 뒤에 와야 한다. 따라서 별개 행 두 개를 같은 y에 두는 것은 불가능하다. 하나의 행에 `[A, B, C, D]`를 넣는 우회는 가능하지만, 그러면 두 메시지 각각의 결과 경계·개별 y 힌트·선택 ID를 어떻게 연결하는지는 별도 어댑터 계약이 필요하다. 합성 행을 만들었다고 개별 요소 지원이 자동으로 해결되지는 않는다.

최초 범위를 **순서대로 쌓는 단일 행**으로 정한다면 현재 제한은 허용할 수 있다. 동높이가 실제 요구가 되면 합성 행과 자식 geometry 매핑, 또는 같은 높이 그룹 중 하나를 검토한다. 지금 범용 부분순서 그래프나 제약 해결기를 도입할 이유는 없다. `par` 프레임의 의미·분기 구조는 계속 다른 팀원의 영역이다.

## 5. 순서와 pin 정책은 타당하지만 충돌 기준을 구체화해야 한다

정렬된 인접 참여자는 `next.x >= current.x + current.width + participantGap`을 만족해야 한다. 인접 행은 `next.y >= current.y + current.height + rowGap`을 만족해야 한다. 엔진이 행 높이를 늘렸다면 최종 높이로 검사해야 한다.

| 사례 | 계산 | 필요한 처리 |
| --- | --- | --- |
| A 폭 80, 간격 20; A x=80, B x=220 고정 | `220 >= 80+80+20` | 두 pin 유지 가능 |
| 같은 조건에서 A x=180, B x=220 고정 | `220 < 180+80+20` | ERROR; 순서를 바꿔 해결하지 않음 |
| A x=180 선호, B x=220 고정 | A는 x≤120이어야 함 | 선호를 옮겼으면 WARNING |
| 세 참여자 폭 80, 간격 20; A x=0, C x=150 고정 | B를 끼우려면 C x≥200 | 두 pin 사이 중간 요소까지 고려해 ERROR |
| r1 y=100·높이 30 고정, r2 y=110 고정, 행 간격 10 | r2 y≥140 필요 | ERROR |

앞의 측정 제약을 추가하면 헤더 박스끼리의 간격만 맞는 pin도 긴 라벨 때문에 불가능해질 수 있다. 새 제약 역시 pin보다 약하게 취급해서 몰래 무시하면 안 된다.

음수 좌표는 이미 허용된다. 따라서 음수 pin 자체가 충돌은 아니다. 캔버스 경계를 이동·확장해 여백을 마련할 수 있다. 화면에 맞추려고 결과 전체를 평행이동하면서 pin까지 바꾸는 구현은 현 계약을 위반한다. 화면 스크롤·확대 변환은 렌더러가 별도로 적용한다.

추가로 합의할 작은 항목은 다음과 같다.

- 참여자 헤더의 공통 y와 자동 배치의 기준 위치. 현재는 헤더 y 정렬 규칙까지 명시하지 않는다.
- 입력이 같을 때 같은 결과를 내는지. 최소 이동 최적화나 전체 편집 이력 전달까지 도입할 필요는 없지만 기본적인 재현성은 유용하다.
- 선호를 이동했다고 판단하는 실수 비교 기준. pin은 여전히 요청한 값을 정확히 보존한다.
- `Diagnostic.elementId`의 이름 공간. 참여자와 행은 같은 문자열 ID를 사용할 수 있으므로, UI에서 정확히 강조하려면 대상 종류를 구분하거나 ID 정책을 합의해야 한다. 모든 의미 요소의 ID를 새로 설계할 필요는 없다.

## 6. 성공 결과의 검증은 요청과 함께 해야 한다

기존 계약·설계 문서는 실제 알고리즘이 없고 결과 조건을 자동 검증하지 않는다는 점을 이미 정확히 밝힌다. 다음은 엔진 구현과 연결할 때 보완할 검증 범위다. `LayoutResult` 생성자는 결과와 요청을 비교하지 않는다. 다음 객체를 만들 수 있고 `hasErrors()`는 false다.

```java
new LayoutResult(Map.of(), Map.of(), Map.of(),
    new Bounds(0, 0, 0, 0), List.of());
```

빈 입력에는 유효할 수 있지만 참여자·행이 있는 입력의 성공 결과라면 잘못이다. 즉 **`hasErrors()==false`는 진단 목록에 ERROR가 없다는 뜻이지, geometry가 검증됐다는 뜻은 아니다.** 현재 테스트의 pin 관련 확인도 요청 데이터가 보존되는지를 검사한다.

최소 제안은 결과 생성자에 모든 책임을 넣기보다, 엔진 구현 시 요청과 결과를 함께 받는 공통 계약 검사 또는 동등한 테스트를 두는 것이다. 정상 결과는 다음을 확인한다.

1. 입력과 출력의 ID 집합 일치, 행별 연결점 개수와 순서 대응.
2. 참여자 크기 보존, 행의 필요 영역 확보, 연결점의 중심 x와 로컬 y 관계.
3. 참여자 순서·최소 간격, 행 순서·최소 간격, 헤더 간격.
4. 실제 측정 영역과 연결점이 캔버스 및 여백 안에 있는지.
5. 모든 pin 보존, 선호 이동 시 WARNING, 불가능한 요청에는 ERROR.

오류 결과는 원래 부분 geometry를 허용하므로 성공 결과의 완전성 검사를 그대로 적용하면 안 된다. 오류 결과로 정상 화면을 갱신하지 않는 호출자 처리도 별도로 확인해야 한다. 이 문서는 검사기를 구현하지 않는다.

## 측정·어댑터 책임의 최소 합의안

권장되는 순서는 **의미 담당자의 결정 → 렌더러의 측정 → 어댑터의 배치 입력 → 엔진의 좌표 → 같은 측정 조건의 렌더링**이다. 실제 모듈 배치와 담당자는 팀이 정한다.

| 책임 | 합의할 내용 |
| --- | --- |
| 의미 모델 담당 | 참여자·메시지의 의미, 안정적인 ID, 의미상 순서와 표시할 요소 |
| 렌더러/측정 담당 | 폰트·크기·줄바꿈·선 굵기·화살표·패딩을 포함한 점유 영역과 기준점 |
| 어댑터 담당 | 의미 결정을 ID·순서·측정 geometry로 변환; 합성 행이면 원본 ID 매핑 유지 |
| 배치 담당 | 전달받은 수치 제약 만족, pin/선호 처리, 결과 영역과 진단 |

첫 버전에서는 같은 데스크톱 렌더러의 논리 좌표 단위를 사용하고, 명시적 줄바꿈이나 고정된 측정 폭으로 크기를 먼저 확정하는 방식이 단순하다. 배치 폭에 따라 자동 줄바꿈하고 높이를 재측정하는 동작이 필요해지면 그때 재측정 절차를 합의한다. 지금 측정 콜백·다단계 렌더 파이프라인·여러 플랫폼용 추상화를 추가하지 않는다.

로컬 geometry 보완도 **참조별 y 오프셋, 기준점에 대한 좌우 점유량, 필요할 때 연결점 사이 최소 거리**부터 검토하면 된다. 이것은 최종 DTO 설계가 아니라 필요한 정보의 목록이다. 여러 기준점에 딸린 도형을 모두 고정된 로컬 좌표로 묶는 방법은 참여자 이동과 충돌할 수 있으므로 실제 예제로 합의한 뒤 타입을 정한다.

## 팀원에게 확인할 세 질문

1. **첫 시퀀스 범위가 무엇인가?** 기본 메시지·자기 호출·좌우 노트 중 어디까지 포함하며, `par` 블록 표시와 같은 높이의 복수 메시지 표시 중 실제 필요한 것은 무엇인가?
2. **측정값을 누가 어떤 규칙으로 넘기는가?** 라벨이 두 연결점 사이에 들어가야 하는지, 줄바꿈·로컬 연결점·돌출량을 누가 결정하는지, 엔진 결과와 같은 조건으로 누가 그리는지 합의할 수 있는가?
3. **표시 ID·순서·드래그 제약을 어떻게 연결하는가?** 한 의미 요소와 배치 행의 관계, ID 유지/삭제, pin과 선호 기본값, 합성 행이 필요할 때 개별 선택·진단·저장 좌표의 매핑은 누가 책임지는가?

답을 받은 뒤 기본 메시지·자기 호출·노트의 작은 입력/기대 geometry와 충돌 사례부터 확정하면 된다. 이번 검토만으로 새 의미 모델, 범용 도형 계층, 제약 해결기, 저장 형식까지 설계할 필요는 없다.

04 · 출력에서 약속하는 것
영역 · Bounds
participantBounds와 rowBounds는 ID별 x, y, width, height입니다. canvasBounds는 여백을 포함한 전체 영역입니다.
연결점 · Point
rowAnchors는 행의 참여자 참조 순서를 유지합니다. x는 참여자 중심, y는 행 위쪽 + offsetY입니다. leftExtent·rightExtent로 연결점 주변 영역을 전달하고, minimumSpans로 연결점 사이 최소 거리를 지정합니다. 선·화살표의 UML 의미는 렌더러가 해석합니다.
진단 · Diagnostic
선호 좌표 조정은 WARNING, 불가능한 고정 좌표는 ERROR입니다. hasErrors()는 반환된 진단만 검사합니다. SequenceLayoutValidator.validate(request, result)의 ERROR도 확인한 뒤 좌표를 사용합니다. target은 PARTICIPANT/ROW와 ID를 함께 전달합니다.

근거와 제안을 구분해서 설명합니다.
위 코드와 구현 상태의 직접 근거는 현재 저장소의 Java 소스와 결과 검증기입니다. 책임 분리, 수동 좌표 정책, 진단 정책은 프로젝트 요구사항을 바탕으로 제안한 계약이며 외부 표준이 요구한 동일한 API가 아닙니다.
Mermaid에서 확인한 관찰: 고정된 커밋의 참여자 배치 코드는 actorKeys 순서로 순회하고 이전 폭·간격을 이용해 x를 계산합니다. 렌더링 흐름은 참여자를 그린 다음 메시지 목록을 처리합니다. 크기 계산 코드는 텍스트 측정과 여백을 사용합니다. 이 관찰을 바탕으로 순서·측정 크기·간격을 배치 입력으로 전달하자는 설계 판단을 했습니다. 현재 Java 타입 이름과 수동 좌표 고정 정책을 Mermaid가 제공한다는 뜻은 아닙니다.
Java 언어 기능의 근거: Java 25 공식 Records 문서는 record의 필드·접근자 등 데이터 표현과 compact constructor의 검증 방식을 설명합니다. 이를 근거로 값 전달용 타입과 생성자 검증을 선택했습니다. record 자체가 내부 컬렉션까지 불변으로 만들지는 않아 코드에서 List.copyOf와 Map.copyOf를 사용합니다.
코드별 선택 이유와 레퍼런스 대응을 Markdown으로 읽기
사용자 조사 자료: Notion 조사 페이지. 조사 노트가 인용한 지정 커밋의 원본을 다시 확인했습니다. 노트의 코드 조사와 실제 브라우저 배치 실측은 구분합니다.

모델 → 배치 → 렌더링이라는 역할은 비슷하지만, 지금의 Java 타입과 고정 좌표 정책은 우리 프로젝트의 제안입니다.
